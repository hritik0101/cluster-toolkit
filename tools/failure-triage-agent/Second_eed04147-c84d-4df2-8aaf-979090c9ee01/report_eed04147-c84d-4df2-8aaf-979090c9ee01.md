# Triage Report for build-id `eed04147-c84d-4df2-8aaf-979090c9ee01`

## Executive Summary
A post-job Slurm epilog script, designed to perform a GPU health check, failed consistently, causing all compute nodes to be drained and rendering the cluster unusable for subsequent jobs. The failure was caused by a critical NVIDIA driver version mismatch, where the kernel-mode driver (580 series) conflicted with the user-space libraries (570 series) due to an upstream package dependency resolution issue during the node image build process.

## Chronology of Events & Forensic Root Cause Analysis

The investigation traced the failure from the visible symptom (pending jobs) back to a subtle package installation conflict. The following causal chain was established:

1.  **Why were integration test jobs stuck in a `PENDING` state?**
    The `squeue` command revealed that jobs were pending because the required compute nodes were unavailable. The reason given was: `(Nodes required for job are DOWN, DRAINED or reserved for jobs in higher priority partitions)`.

2.  **Why were the compute nodes unavailable?**
    The `sinfo` and `scontrol show nodes` commands confirmed that all nodes in the `a3` partition (`a3hspeed04-a3nodeset-[0-1]`) were in a `DRAIN` state. The reason for the drain was explicitly stated as `Epilog error`. This indicates that a script configured to run after a job completes (`epilog`) failed, and Slurm's safety mechanism correctly took the node out of service to prevent further failures.

3.  **Which epilog script failed and why?**
    The `slurmctld.log` on the controller node showed errors for `job_epilog_complete` immediately after `JobId=1` finished. The `slurmd` journal on the compute nodes provided the specific error: `epilog failed status=226:0`. The blueprint (`a3high-slurm-blueprint.yaml`) defines a partition-specific epilog that symlinks `/slurm/scripts/tools/gpu-test` to run on job completion. This script, which uses `dcgmi` to perform a GPU health check, was the source of the failure. The exit code `226` is not standard, but the `slurmd` journal log shows the script itself exited with an error.

4.  **Why did the `gpu-test` script fail?**
    The `gpu-test` script is designed to run `dcgmi diag` to check GPU health. The log file for this script, `/var/log/slurm/chs_health_check.log`, ends abruptly after starting the DCGM health check. Simultaneously, the kernel `dmesg` log on the compute nodes recorded a `general protection fault` (a kernel-level crash) within a GPU-related process (`tcpgpudmarxd`). This proves the GPU driver stack was critically unstable and crashed when the diagnostic tool attempted to interact with it.

5.  **Why was the GPU driver stack unstable?**
    The `dmesg` log provides the definitive root cause: a version mismatch between the loaded NVIDIA kernel module and the user-space components. The kernel explicitly logged: `nvidia-nvswitch: Version mismatch, kernel version 580.159.03 user version 570.211.01`. This conflict is catastrophic and explains the subsequent kernel panic. A review of the installed packages via `dpkg -l` confirmed a mixed environment where packages from both the `nvidia-570-server` and `nvidia-580-server` series were installed. The blueprint intended to install the `570` series, but the `apt` package manager resolved dependencies for other packages (like `datacenter-gpu-manager`) by pulling in components from the newer `580` series, creating an unsupported and broken hybrid driver installation.

## Recommended Remediation

The root cause is a package dependency conflict originating from the upstream OS repositories. The blueprint attempts to install the `nvidia-driver-570-server-open` metapackage, but `apt` is pulling in conflicting `580`-series dependencies for other requested packages.

The most direct and robust solution is to enforce a consistent driver version across all installed components by updating the package list in the image creation script. Since the package manager appears to be defaulting to installing `580`-series kernel modules, we will align all user-space packages to match this version.

Modify the `configure_gpu_packages.yml` runner within the `a3high-slurm-blueprint.yaml` file to explicitly install the `580` series for all related packages.

**File:** `examples/machine-learning/a3-highgpu-8g/a3high-slurm-blueprint.yaml`

**Change:**

```diff
--- a/examples/machine-learning/a3-highgpu-8g/a3high-slurm-blueprint.yaml
+++ b/examples/machine-learning/a3-highgpu-8g/a3high-slurm-blueprint.yaml
@@ -202,10 +202,10 @@
               package_url: https://developer.download.nvidia.com/compute/cuda/repos/{{ distribution }}/x86_64/cuda-keyring_1.1-1_all.deb
               package_filename: /tmp/{{ package_url | basename }}
               nvidia_packages:
               - cuda-toolkit-12-8
-              - nvidia-dkms-570-server-open
-              - nvidia-driver-570-server-open
+              - nvidia-dkms-580-server-open
+              - nvidia-driver-580-server-open
               - datacenter-gpu-manager
-              - libnvidia-nscq-570
+              - libnvidia-nscq-580
               - nvidia-container-toolkit
             tasks:
             - name: Download NVIDIA repository package

```

This change standardizes the installation on the `580` driver series, ensuring that the kernel module and all user-space libraries and tools are version-aligned, which will resolve the conflict and prevent the `dcgmi` crash.
